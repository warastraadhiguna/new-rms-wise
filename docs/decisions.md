| 2026-11-20 | Returns and credit payments at any store (option B, read-only replicas). Return window is a setting. |
| 2026-11-20 | Loyalty points and customer credit usable offline; HQ flags overuse after sync. |
| 2026-11-20 | Prices may differ per branch; setting to force uniform prices. |
| 2026-11-20 | All rupiah rounding goes through `Pos.Shared.Money.Rupiah`. Storage precision is 4 dp; unit prices keep 4 dp. Sale line gross is rounded to the currency precision before discounts; discount and line total are at currency precision, with `line_total = gross - discount`. Midpoints round away from zero. |
| 2026-11-20 | Cash rounding modes are signed: `up` = toward +infinity, `down` = toward -infinity (also for refunds), so a mode always favours the same party. `nearest` rounds an exact half step away from zero. |
| 2026-11-20 | Sale line discount: percent first on the gross, then a nominal amount per line; capped so the line total is never negative. |
| 2026-11-20 | Stock is split into expiry buckets per location + product. The null bucket means no/unknown expiry (`stock_balances.expiry_key = 9999-12-31`); `9999-12-31` is never accepted as a real expiry. Only the null bucket may go negative. Allocation logic is `Pos.Shared.Stock.StockAllocator`. |
| 2026-11-20 | Outbound (sale, delivery, transfer out) is FEFO: dated buckets with positive stock, earliest expiry first; same-date buckets are merged, so the result never depends on input order. Expired buckets (`expiry < today` in the branch timezone) are skipped unless `allowExpired`; expiring today is still sellable. The shortage goes to the null bucket. |
| 2026-11-20 | Inbound (receipt, return, transfer in) with expiry E: a negative null bucket is covered up to 0 first (goods sold while short are assumed to come from this delivery), the rest goes to bucket E. Inbound without expiry goes to the null bucket. Negative dated buckets are never covered. |
| 2026-11-20 | `track_expiry = false`: outbound first drains any remaining dated buckets FEFO (expired included), then the null bucket; inbound always goes to the null bucket. Lets a product switch the flag off without stranding dated stock. |
| 2026-11-20 | One document line produces one `stock_ledger` entry per expiry bucket. Ledger ids are UUID v7, `base_qty` is signed (+ in, - out), `occurred_at` must be UTC, `doc_type` must be one of `StockDocTypes`. |
| 2026-11-20 | Transfers keep the expiry of each FEFO allocation. Within a node: one `LOCATION_TRANSFER` with out entries at the source and in entries at the destination (`StockTransfer.Transfer`). Across nodes: the sender's delivery has one line per expiry; the receiver's goods receipt reads those expiries (`StockTransfer.AllocateReceipt`), covering a negative null bucket earliest expiry first. Total out == total in. |
| 2026-11-20 | "Today" for expiry checks is the branch-local date of the Node Service UTC clock (`BranchClock.Today`, IANA timezone from `branches.timezone`). |
| 2026-11-20 | Database server: MySQL 8.0.19+ only (upsert alias syntax); MariaDB is refused at startup. Every connection runs in UTC. Deadlocks (1213) and lock wait timeouts (1205) re-run the whole transaction up to 3 times. |
| 2026-11-20 | Node identity comes from setting `Node:Code`; the node row arrives with master data, so endpoints that need it answer 503 until it exists. |
| 2026-11-20 | Document numbers `{NODE}-{TYPE}-{YYYYMM}-{000001}` from `document_sequences`, month in the branch timezone. The sequence row is locked until the document commits, so numbers are unique and gapless (a rollback returns the number). Type codes: `SL` sale, `SH` cashier shift, `ADJ` stock adjustment. |
| 2026-11-20 | API and sync JSON: snake_case, decimals as strings with 4 decimals, times ISO-8601 UTC with milliseconds (`PosJson`). Each document writes its `sync_outbox` row (full payload) in the same transaction. |
| 2026-11-20 | Cashier shifts: one OPEN shift per device (device row locked while opening). Close computes `expected_cash = opening_cash + cash tendered - change given` over cash payment methods; sales hold a shared lock on their shift so a close waits for them. Shift is a mutable document: open = row_version 1, close = 2, each with an outbox row. Cashier/device come from the request until authentication exists. |
| 2026-11-20 | Sales (`POST /api/v1/sales`): the client generates the sale id (UUID v7); the same id again returns the stored sale (200, `replayed: true`, no warnings), also when sent concurrently. The device must have an open shift; `created_by` is the shift's cashier. One transaction (with retry): FEFO stock posting (`SALE`, one ledger row per expiry per line), number, sales + lines + payments, outbox. |
| 2026-11-20 | Sale prices come from the server. Per `min_qty` tier the latest `effective_from <= now` (ties: lower price). The best tier (largest `min_qty <= qty`) is looked up in the branch rows and in the default rows; the larger `min_qty` wins, and on equal `min_qty` the branch price wins. (Revised: branch and default tiers are compared, not "branch set first".) |
| 2026-11-20 | Sale payments: amounts sent are money handed over. Cash rounding (`rounding.cash_step` / `rounding.cash_mode`) applies only when the sale includes cash. Non-cash + credit may not exceed the total (change only from cash); one cash payment per sale. `sale_payments.amount` is the applied part; cash also stores `tendered` and `change_given`. |
| 2026-11-20 | Credit: needs a customer; `credit_limit` NULL = no credit facility (rejected). Over the limit (local data: non-voided credit sales minus receivable payments at this node) is allowed with warning `credit_limit_exceeded`. `due_date` = branch-local sale date + `payment_term_days`. |
| 2026-11-20 | TODO: promotions (`promotion_id` stays NULL), tax (`tax_amount` = 0 on lines and header), limits on manual line discounts, uniform-price setting, audit log for approved line deletions. |
| 2026-11-20 | Sale (header) discount: `discount_pct` OR `discount_amount`, applied to the sum of line totals, rounded to the currency precision, capped at the subtotal; cash rounding comes after it. Limit per cashier from permission `discount.max:N` (largest N; `*` = no limit; none = 0%). The allowed amount is rounded like the discount, so an exact N% never needs approval. Above the limit: a one-time approval token (action `sale.discount.override`) or supervisor username + password in the request; `sales.discount_approved_by` records the supervisor. Otherwise 403 `discount_approval_required`. |
| 2026-11-20 | Supervisor approvals: `POST /api/v1/auth/approve` (logged-in user + supervisor username/password + action `sale.line.delete` or `sale.discount.override`). The supervisor needs that action as a permission; wrong passwords count toward the same lockout as login; wrong password = 403 `approval_rejected` (not 401, the cashier stays logged in). Returns a one-time token valid 2 minutes, only for the requesting user; stored hashed in node-only `approval_tokens` and consumed in the document transaction. |
| 2026-11-20 | `products.allow_qty_multiplier` (default 1): 0 means each item is scanned on its own line; the server refuses qty > 1 (`qty_multiplier_not_allowed`). |
| 2026-11-20 | Cashier lookups: `GET /api/v1/products/search?q=` (exact barcode, exact SKU, then every name word; max 50; effective branch price for qty 1 plus price tiers; stock summed over sellable locations) and `GET /api/v1/customers/search?q=` (code, phone digits, name words; credit limit/outstanding/remaining and points from local data). `GET /api/v1/shifts/current` returns the device's open shift. Login responses include the node (id, code, name). |
| 2026-11-20 | Authentication at the node, offline: `POST /api/v1/auth/login` (username + password) and `/auth/pin` (username + PIN; kept for a possible Android client, not used by the desktop). Passwords and PINs are bcrypt (`$2y$`, cost 12) like Laravel at HQ. The node issues HS256 JWTs (issuer/audience `pos-node:{NODE}`, lifetime `Auth:TokenLifetimeHours`, default 12) with its own 64-byte key, created on first start at `Auth:KeyPath` (default `%ProgramData%\PosNodeService\keys\jwt-signing.key`, DPAPI machine scope on Windows), never committed. Replacing the key logs everyone out. |
| 2026-11-20 | Permissions = union of `roles.permissions` (JSON array, `*` = all) over `user_roles` with `node_id` NULL or this node. A user without any role at this node gets 403 `no_access_to_node` after a correct password. Endpoints: `shift.open`, `shift.close`, `sale.create`. Cashier / `created_by` come from the token; `cashier_id`/`device_id` were removed from request bodies. |
| 2026-11-20 | Every authenticated request re-checks the user in the local database (cached per user, `Auth:UserCacheSeconds`, default and maximum 30 s): inactive or deleted users get 401 `user_inactive` even with an unexpired token. Effective permissions = token permissions that the user still has at this node (revocations apply within the cache time; new grants need a new login). |
| 2026-11-20 | Only the shift owner (`cashier_shifts.cashier_id` = logged-in user) may sell on a shift (403 `not_shift_owner`), unless the user has `shift.share` (`*` includes it). Changing cashier = log in, close the previous shift, open an own shift. |
| 2026-11-20 | Device is sent in header `X-Device-Id` and must be an ACTIVE device of this node (400 `device_required`, 403 `device_not_allowed`) until full device activation exists. |
| 2026-11-20 | Lockout: 5 consecutive failed attempts (password and PIN together) lock a login name for 5 minutes (429 `account_locked` with `retry_after_seconds`). Tracked per normalised login name in local table `login_throttle` (users are HQ data), also for unknown names; unknown/inactive/deleted users and wrong secrets all answer 401 `invalid_credentials` and always run one bcrypt check. |
| 2026-11-20 | Desktop (WPF): MVVM with CommunityToolkit.Mvvm and Microsoft.Extensions.Hosting DI. Per-PC settings in `%ProgramData%\PosDesktop\settings.json` (`node_service_url`, `device_id`); a missing file is created as a template and the app explains what to fill in. ViewModels and the HTTP client do not depend on WPF and are tested in `Pos.Desktop.Tests` (fake server / fake API); views only bind. UI text is Indonesian; the client maps problem codes to Indonesian messages and reports an unreachable Node Service clearly. |
| 2026-11-20 | After login the device's open shift decides the next screen: own shift → main window, none → open shift, another cashier's → refused with a message (that shift must be closed first). Passwords are cleared from the ViewModel right after each attempt. |
| 2026-11-20 | **UI kasir mengikuti tata letak, istilah, dan shortcut aplikasi lama (RMS 2). Perbaikan dilakukan tanpa mengubah kebiasaan kasir.** (Owner's decision.) |
| 2026-11-20 | Owner's decision, following RMS 2: the desktop login is username + password only (no PIN mode). Supervisor approvals (`sale.line.delete`, `sale.discount.override`) use the supervisor's username + password, in `/auth/approve` and in the sale request (`supervisor_username` / `supervisor_password`); the lockout still applies. `/auth/pin` stays in the backend for a possible Android client. |
| 2026-11-20 | API errors are RFC 7807 problem details with a stable snake_case `code` (422 validation, 409 state conflict, 404 unknown, 503 node not configured). |
| 2026-11-20 | Dev data comes from `dotnet run --project src/node/Pos.NodeService -- seed-dev` (refuses databases not named `*_dev`), never from a migration. Opening stock is posted through a real ADJUSTMENT document. |

## Setting keys

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `rounding.cash_step` | decimal string | `"0"` | Cash totals are rounded to a multiple of this (e.g. `"100"`, `"500"`). `0` = no rounding. |
| `rounding.cash_mode` | string | `"nearest"` | `up`, `down` or `nearest` (see `CashRoundingModes`). |
| `currency.decimals` | integer 0..4 | `0` | Currency precision for line discounts and line totals. |

# CLAUDE.md — POS Multi-Branch (project rules)

Read this file fully before every task. These rules are not optional.

## Communication
- Talk to the user in **Indonesian**. Write all code, identifiers, comments, commit messages,
  table/column names and API fields in **English**.
- The user is an experienced programmer. Be concise; explain decisions, not basics.
- Work in small steps. One task = one feature with its tests. Stop and report when done.

## What we are building
An offline-first, multi-branch POS.
- **HQ** (Ubuntu server): Laravel + MySQL. Web admin, master data, purchasing, accounting, monitoring.
- **Node** = one physical site (store `TK01`, warehouse `GD01`, ...). Each node runs on ordinary
  Windows PCs: one PC hosts MySQL + **Node Service**; other PCs/tablets are clients.
- **Node Service**: ASP.NET Core (.NET 10) running as a Windows Service. Local REST API for every
  client in the node, the only place business rules run, and the sync agent to HQ.
- **Clients**: WPF (.NET 10) for cashier / store admin / warehouse; Android (Kotlin) later.
  Clients never connect to MySQL directly and never hold DB credentials.
- A node must keep working with no internet. Internet is only for syncing with HQ.

Full design: `docs/` (architecture summary + decisions). Schema: `database/migrations/`.

## Data rules (never break these)
1. **Single writer.** Every row has one owner. Master data and purchase orders: HQ.
   Node documents: the node in `node_id`. Nobody else updates that row. A decision by another
   party (e.g. HQ approving a stock count) is a separate row owned by that party.
2. **Replicas are read-only.** A node may hold copies of other nodes' documents (e.g. a customer's
   sales from another store for returns/credit payments). A node only pushes rows where
   `node_id` = its own node.
3. **Ids.** Synced tables: UUID v7 as `CHAR(36) CHARACTER SET ascii`, generated by the owner
   (`Guid.CreateVersion7()` in C#). Local-only and HQ-internal tables: `BIGINT AUTO_INCREMENT`.
   Users see document numbers like `TK01-SL-202611-000123`, never UUIDs. Codes created at a node
   (new customers, temporary products) are prefixed with the node code.
4. **No hard deletes.** Master data uses `deleted_at` + a new `version`. Documents are never
   deleted or edited after completion; corrections are new documents (void, return, adjustment,
   reversing journal).
5. **Stock = ledger.** `stock_ledger` is INSERT-only; `stock_balances` is a cache updated in the
   same DB transaction. Stock is always in the product's **base unit** (`base_qty`).
   Sales are allocated **FEFO** across expiry dates by the Node Service, never chosen by the cashier.
   Negative stock is allowed.
6. **Money/qty:** `DECIMAL(18,4)` in MySQL, `decimal` in C#, decimal strings in JSON
   (`"12500.0000"`). Never `float`/`double`. Rupiah rounding lives in ONE helper in `Pos.Shared`.
7. **Time:** store UTC (`DATETIME(3)`), convert to the branch timezone only for display/reports.
   Event times come from the Node Service clock, not client PCs.
8. **Status/type columns are VARCHAR**, values defined as C# enums/constants, not MySQL ENUM.
9. **Outbox.** Every document saved at a node writes its `sync_outbox` row in the same transaction.
   Mutable documents carry `row_version`; HQ keeps the highest version. Sync is idempotent.

## Business decisions already made
- Cost of goods: **moving average** per product per entity, computed only at HQ.
  Sales at negative stock use a provisional cost and are corrected when goods arrive.
- All purchasing goes through HQ (POs). Warehouses receive goods against POs.
- Returns and credit payments are allowed at any store (via replicas). Return window is a setting
  (`returns.window_days`).
- Loyalty points and customer credit can be used offline; HQ flags overuse after sync.
- Prices may differ per branch (`prices.branch_id`); a setting can force uniform prices.
- Physical-goods work happens locally (sales, receiving, transfers, counting). Decisions, purchasing,
  money and accounting happen at HQ.

## Schema changes
- Never edit a migration that may have been applied. Add a new file:
  `database/migrations/NNNN_short_description.sql` (next number, 4 digits).
- Node Service applies migrations at startup with DbUp. Laravel runs the same SQL files.
- EF Core is used for data access only — **no EF migrations**.

## C# conventions
- .NET 10, nullable enabled, implicit usings, file-scoped namespaces.
- Business logic goes in `Pos.Shared` as plain classes with no DB/UI dependency, so it is testable.
- WPF uses MVVM (CommunityToolkit.Mvvm). No business logic in code-behind.
- **The cashier UI follows the layout, terms and shortcuts of the old application (RMS 2).**
  Improvements must not change cashiers' habits. When unsure how RMS 2 does something, ask before
  designing a new layout, flow or key.
- **Every WPF UI change needs at least one test that interacts through real controls**
  (create the window on an STA thread, type into the TextBox/PasswordBox, press Enter or invoke the
  button, then assert on the ViewModel or the API call). ViewModel-only tests do not count: they cannot
  catch broken bindings. See `Pos.Desktop.Tests/UiInteractionTests.cs`.
- **Every search (a search box with a results grid) uses the `SearchNavigation` behavior**
  (`Pos.Desktop/Infrastructure/SearchNavigation.cs`): set `infra:SearchNavigation.Results="{Binding ElementName=Grid}"`
  on the search TextBox and give the grid an Enter KeyBinding. Keys: Down in the box → first row; Up/Down move rows;
  Enter takes the highlighted row; Up on the top row → back to the box (text kept, caret at the end); typing a
  character in the grid → it becomes the new text of the box (barcode scans keep working). After an item is taken,
  focus returns to the box. New searches need real-control UI tests for these keys (see `SearchNavigationUiTests.cs`).
- **Integration test data never collides:** unique values (usernames, codes, numbers) come from a Guid or a
  per-run counter, never from a small random range (`"X" + Random(100, 999)` once collided on a unique key and made
  a test flaky). Each test uses its own users; only tests about the dev seed itself log in as seeded users, and
  only with the correct password (so lockout and caches are never shared between tests).
- Node Service: minimal APIs grouped by feature; MySqlConnector + EF Core 9 (Pomelo 9) or Dapper.
- Async all the way for I/O. Pass `CancellationToken`.

## HQ (Laravel) — src/hq
- Laravel 13 + official React starter kit (Inertia + React + TypeScript), Pest 4. Production runs **PHP 8.4**
  (the laptop has 8.5): `composer.json` keeps `config.platform.php = 8.4.0` and `require.php = ^8.4`.
  Never use PHP 8.5-only features (pipe operator `|>`, etc.).
- MySQL 8.4 (server port 3307). Local WAMP: `pos_hq_dev` (dev) and `pos_hq_test` (tests), user `pos_app`.
  `.env` is git-ignored; `.env.example` lists every key.
- **Schema:** the domain schema comes ONLY from `database/migrations/*.sql` via `php artisan pos:migrate`
  (`App\Support\Schema\SqlMigrator`): name order, statement by statement, UTC session, journal `schema_versions`
  with DbUp's exact table and script names — one database can be migrated from the node or HQ without repeats.
  Laravel migrations (`src/hq/database/migrations`) are for framework tables only (sessions, cache, jobs);
  none may touch a domain table (a test checks this). New domain tables/columns = a new numbered SQL file.
- UTC everywhere (app timezone and MySQL session `+00:00`); screens convert to the branch timezone
  (`config('pos.display_timezone')`, default Asia/Jakarta). InnoDB (WAMP defaults to MyISAM).
- Money/qty never float in PHP: decimal strings (`'decimal:4'` casts) and `App\Support\Decimal` (brick/math),
  which rejects floats.
- UI text in Indonesian; code, tables, columns, routes' code in English (menu paths may be Indonesian words).
- **Login:** our `users` table (UUID string key, `username`, bcrypt `$2y$` `password_hash` shared with the nodes),
  `App\Auth\HqLogin`: same throttle as the node (`login_throttle`, 5 failures = 5 minutes, also for unknown names),
  one message for every failure ("Username atau password salah."). No registration, email verification,
  password reset, 2FA or passkeys. Inactive/deleted users are refused and lose their session on the next request.
- **Permissions:** `roles.permissions` + `user_roles` like the node (`node_id` NULL or the HQ node, `"*"` = all).
  Every HQ page needs `hq.access` (middleware `hq`, re-checked per request). Per page: middleware
  `permission:a.b[,c.d]` or gates (`can:a.b`, `Gate::allows`) — every ability is a permission.
- **Master data writes go ONLY through `App\Support\MasterData\MasterDataWriter`** (`create`/`update`/`delete`):
  one transaction, `master_version.last_version + 1` under `SELECT ... FOR UPDATE`, the row's `version` set,
  UUID v7 ids, soft delete (`deleted_at` + new version), `audit_logs` (user, table, id, action, old/new, IP).
  Never `Model::save()` / `DB::table()->update()` on master data in application code.
- Dev data: `php artisan pos:seed-dev` (entity E01, branch B01, nodes HQ and TK01, role OWNER `"*"`,
  user `admin` / `admin123`); refuses databases not named `*_dev` / `*_test`.
- Run: `cd src/hq && composer install && npm install && cp .env.example .env && php artisan key:generate`,
  then `php artisan pos:migrate && php artisan migrate && php artisan pos:seed-dev`, `composer dev` (or `npm run build`
  and `php artisan serve`).
- Test: `php artisan test` (rebuilds `pos_hq_test` once per run: drop all, `pos:migrate`, `migrate`; tests use their
  own unique users, never the seeded ones). Before committing: `vendor/bin/pint`, `vendor/bin/phpstan analyse`
  (level 7, no ignores), `npm run check`, `npm run types:check`, `npm run build` — all clean.

## Definition of done (every task)
1. Tests written first for the logic in `Pos.Shared` (xUnit), including edge cases
   (zero, negative stock, rounding, unit conversion, multiple expiry dates).
2. `dotnet build src/node/Pos.slnx` passes with no warnings you introduced.
3. `dotnet test src/node/Pos.slnx` passes. HQ tasks: `php artisan test`, Pint, PHPStan and `npm run build` in `src/hq`
   pass (see "HQ (Laravel)").
4. Short report to the user (in Indonesian): what changed, how to try it, anything left open.
5. Suggest a commit message in English. Do not commit or push unless asked.
